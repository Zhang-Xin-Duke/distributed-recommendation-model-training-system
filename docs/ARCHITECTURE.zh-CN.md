# 分布式参数服务器（Distributed Parameter Server）

项目负责**训练参数的分布式存储、访问与更新**。

首版聚焦稀疏 Embedding 参数，打通一条完整链路：按 ID 取向量，组织训练特征，接收反向梯度，更新参数，管理 CPU/GPU 之间的缓存和迁移。

这里的“稀疏”主要指每批只访问大参数表中的少量行，单行向量通常仍是稠密的。
这个模式适用于广告、推荐、知识图谱、带可训练节点向量的图学习和部分词向量训练。

## 保留主框架，抽出独立服务

Entropy 继续负责读数据、构图、模型前向与反向、dense 参数更新、多卡同步和任务运行。
我们从参数访问边界抽出一个独立 C++ 服务，由轻量适配器对接原来的 Pull/Push/Join。

服务管理参数表、批量查找、pooling、梯度归并、稀疏优化器和缓存决策。
GPU cache agent 在显存中保存权重和 Adam 状态，完成查找、聚合、更新和状态传输。
`WorkerCacheAgent` 可由依赖兼容的原生训练进程直接持有，也提供独立进程入口；两者通过同一 BRPC 接口接入参数分片。
本地设备读取与远端控制共用准入队列和有序执行器；返回的设备结果独立持有显存，供模型 stream 消费。
[原生 Worker 接入与生命周期](WORKER_AGENT.md) 说明接口、关闭顺序和 TensorFlow 原生设备接入范围。
原生 C++ 适配器的 `PullDevice` 可将 CPU、本地 GPU 与远端 Agent 的贡献在模型 GPU 上合并，
完成全局 mean 归一化和 sequence padding 还原，再沿用现有句柄回传梯度；
`PullPreparedDevice` 复用输入预准备队列。[设备端完整特征路径](DEVICE_PULL.md) 已通过真实 CUDA 训练轨迹对照。
TensorFlow 原生 CPU/CUDA 算子已接通 Pull/Push/Join：直接返回模型可用的特征张量，
接收自动求导产生的梯度，再等待参数更新确认；模型与 dense 优化器保持原有职责。
原生模块通过版本化 C 接口隔离 BRPC/Protobuf 与 TensorFlow 的二进制依赖，
另保留便携 host callback 接入路径。[原生算子与验证](NATIVE_TENSORFLOW.md)。

这样，参数服务可以独立启动、分配 CPU/内存和扩容；训练模型保持原有运行方式。

## 三个角色

| 角色 | 责任 |
|---|---|
| 原有 Learner / GPU Worker | 提供训练输入，执行模型，产生梯度 |
| 独立参数服务 | 存储与访问参数，执行 sparse 更新，决定缓存放置和迁移 |
| GPU cache agent | 查显存中的常驻行，执行更新，批量换入与回写完整状态 |

## 一批请求怎样走

1. Learner 发来表、ID 和样本分段信息；服务去重，保留每个 ID 的原位置。
2. 服务区分 CPU 参数行和 GPU 常驻行，返回或组织图需要的特征。
3. 原模型照常前向、计算 loss 和反向。
4. 梯度带着本次 lookup ticket 返回，合并该次请求内重复 ID 的贡献，更新对应参数。
5. GPU 与 CPU 完成各自负责的更新，服务回复确认；完成 Push/Join 后释放本次引用。

一次 Push 涉及多张卡时，向不同 GPU 并发下发更新；同一张卡上的控制命令保持顺序。
CPU 与所有 GPU 部分使用该次请求的同一份优化器上下文，不合并不同 Learner 的更新。

保留原框架的异步 Learner 模式；不同 Learner 的 Adam 更新仍是独立更新，服务不把它们合成一次。

## 我们具体优化什么

**访问路径：** 根据特征长度、重复率和各阶段实际成本，选择 CPU 先聚合还是将去重向量交给 GPU。
例如 100 个 128 维 FP32 向量约 50 KiB，求和后只有 512 B；但 CPU 繁忙或 ID 重复较多时，其他路径可能更合适。

**缓存准入：** 参数迁移需要同时搬权重和优化器状态。比较后续复用节省与换入、回写成本，减少只用一次的参数进入缓存。
未进入缓存的参数继续正常训练。

**迁移调度：** 限制迁移字节与批次数，预留空槽，按兼容布局批量传输完整状态。
当前迁移要求相关 lookup 已结束，等待 GPU 完成后才发布新位置与 generation；回写确认后才回收显存槽。
已实现按访问窗口触发的自动准入与替换，并限制迁移字节、批次数与空槽预留。
异步请求准备已实现：独立线程提前去除 padding、按分片组织 ID 并生成位置映射，
由批次数与字节预算限制在途准备工作；实际读取参数仍在消费该批次时发生。
迁移、更新等待 Agent 时，操作可挂起并交还分片线程；不冲突的请求继续推进。
参数行、同表优化器和 Agent 控制流由依赖调度保持顺序；实际缓存维护窗口会升级为全局屏障。

分片、去重、pooling、GPU cache 和异步传输在 Entropy 中已有参考。独立项目重点是上述决策、服务化边界和完整参数生命周期。

### 自动缓存准入与淘汰

请求成功读取后，按不同参数行记录一次访问，重复 ID 和重试不重复计数；
Push 或 Release 完成后按窗口决策。控制器维护有界、随时间衰减的访问记录，
比较后续复用收益与完整参数状态的加载、写回成本。缓存不足时，优先淘汰收益更低、
已达到最短驻留时间且未被在途请求持有的同表参数，再加载新热点。

每个窗口共享迁移字节、批次数和行数上限；Agent 在实际分配时原子检查预留槽位，
防止多个参数分片同时占用预留容量。准入失败保留 CPU 回退；淘汰后的权重、
Adam 状态与更新计数一并回到 CPU，继续正常训练。保存时停止自动决策并写回缓存，
恢复后从新请求重建热点统计。支持 manual、frequency 和 reuse_cost 三种模式。

原生及独立进程的 Host 引用后端已验证热点替换、行引用保护、失败回退和精确恢复；
新增自动策略与 CUDA 预留检查已在 A6000 上验证：CPU/CUDA 检查 17/17、额外 CUDA 进程检查 3/3。
两组固定轨迹共完成 36 轮运行、6,528 次更新，全部触及行的最终权重与 Adam 状态均与 CPU 重放一致。
[成本、吞吐和迁移量对照](CACHE_POLICY_RESULTS.md)。窗口决策目前在分片屏障内执行，
异步输入准备和远端等待解耦均已实现；完成操作进入决策窗口时先等待其他在途操作结束，
再在全局屏障内维护缓存。[完整设计与配置](CACHE_POLICY.md)。

### 等待设备时继续处理无关请求

分片保留一个线程管理参数状态。向 Agent 提交更新或迁移后，以 C++20 协程挂起该操作，
完成线程收到 future 结果后，将续执行排回分片线程。等待期间可处理其他参数行的读取；
相关行的读取、同表 Adam 更新及同一 Agent 控制流继续按顺序执行。
保存采用完整屏障，等待之前的操作完成后再检查引用、回写缓存并落盘。
新增活跃/等待操作数及保留字节统计，配合阶段计时观察并发和排队。
当前 A6000 完整检查 29/29、额外强制 CUDA 检查 5/5 通过。

### 提前准备下一批输入

训练线程执行当前批次时，独立工作线程可提前完成下一批 ID 的 padding 过滤、
分片路由和序列位置映射。准备完成后返回 FIFO token；训练图消费 token 时才向
参数服务发起读取，因此可先完成上一批梯度更新，再读取下一批所需的当前参数。
准备队列同时限制批次数和保留字节；取消正在准备的任务后，仍保留其预算直到线程释放缓冲区。
保存前必须消费或取消剩余 token，并完成现有 Push/Join。

新增八项服务端计时，分别记录读取准备、梯度整理、GPU 数据包准备、更新提交、
CPU 优化器、Agent 等待、迁移和维护窗口耗时。维护包含迁移，迁移可能包含等待，
这些计时存在嵌套，不能相加当作互斥的 CPU 时间占比。
[接口、生命周期与使用示例](ASYNCHRONOUS_PREPARATION.md)。
